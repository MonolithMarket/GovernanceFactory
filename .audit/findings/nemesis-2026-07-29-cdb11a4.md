## NM-011 (MEDIUM) — Anyone can restart the sGOV reward period for 1 wei, diluting and redirecting revenue

**Discovery path.** Feynman Category 3 (consistency) asked why the two permissionless funding
entry points in this codebase are guarded differently:

| Entry point | Permissionless? | Guard against notifying during a live period |
| :-- | :-- | :-- |
| `StakingRewardsFunder.fundNextTranche()` | yes | **yes** — `if (block.timestamp < periodFinish) revert PreviousTrancheActive` (`StakingRewardsFunder.sol:65-66`) |
| `RevenueRouter.distribute()` | yes | **none** |

The State pass then confirmed the consequence: `_startReward` unconditionally rewrites the coupled
pair (`rewardRate`, `periodFinish`) on every call, with no rate limit and no caller restriction
reachable from outside.

**The gap.** `StakedGovToken.notifyRewardAmount` is protected by `onlyRewardsDistribution`
(`StakedGovToken.sol:180`), which looks like access control. Its sole holder is `RevenueRouter`,
whose `distribute()` is `external` with **no modifier at all** (`RevenueRouter.sol:54`). So the
guard is decorative — the privileged call is reachable by any address.

`distribute()` sizes the payout from `coin.balanceOf(address(this))` (`RevenueRouter.sol:57`), which
is donation-sensitive, and forwards it whenever `govStakingAmount != 0`. With the factory default
`govStakingBps = 10_000`, **1 wei of Coin donated to the router is enough** to force a notify. Then:

```solidity
// StakedGovToken.sol:195-218
function _startReward(uint256 reward) internal {
    uint256 rewardToDistribute = reward;
    if (block.timestamp < periodFinish) {
        rewardToDistribute += (periodFinish - block.timestamp) * rewardRate;  // absorb the remainder
    }
    ...
    rewardRate = newRewardRate;
    periodFinish = block.timestamp + rewardsDuration;   // <-- unconditional 30-day reset
}
```

Every call absorbs the entire undistributed remainder and re-stretches it over a **fresh 30 days**.

**Trigger sequence (PoC `testAnyoneCanRestartTheSGovRewardPeriodWithDust`).**

1. Alice stakes 1,000 GOV — she is the only sGOV holder.
2. 30,000 Coin of genuine revenue arrives; `distribute()` starts a 30-day stream.
3. Mallory calls `distribute()` **once per day for 30 days**, donating 1 wei of Coin each time.
4. At day 30 the stream should be complete.

**Measured result:**

| | Baseline (no attacker) | Under attack |
| :-- | --: | --: |
| Revenue delivered by day 30 | 30,000.00 (100%) | **19,150.15 (63.8%)** |
| `periodFinish` | day 30 | **day 60** |
| Attacker cost | — | **30 wei of Coin** + gas |

The remainder is `(29/30)^30 ≈ 36.2%` of the revenue, exactly as the arithmetic predicts. There is
no cap: each call adds up to another 30 days, so the tail can be deferred indefinitely.

**This is value transfer, not just griefing** (PoC `testSuppressThenStakeCapturesOtherStakersRevenue`).
The attacker suppresses the stream while someone else is the sole staker, *then* stakes:

| | Value |
| :-- | --: |
| Alice's revenue with no attack | 30,000.00 |
| Alice's revenue after the attack | **24,575.08** |
| Mallory's revenue — staked only at day 30, after the stream should have ended | **5,424.92 (18.1%)** |

Mallory captured 18.1% of revenue that accrued entirely before she staked, for 30 wei plus gas.

**Consequences.**
1. The 30-day streaming guarantee can be broken by any anonymous address, permanently and repeatably.
2. Revenue is redistributable from early stakers to a late staker who pays only gas.
3. Even with no attacker, every legitimate `distribute()` call resets the clock — so frequent
   (desirable) revenue routing perpetually defers the tail of each prior distribution.

**Why the prior pass missed it.** It correctly enumerated `_startReward`'s two callers and
correctly noted the `depositFor` flush is gated on `block.timestamp >= periodFinish` — then treated
`onlyRewardsDistribution` as terminating the reachability analysis, without asking whether the
holder of that role itself has a public entrypoint.

**Fix.** Mirror the guard the sibling funder already has:

```solidity
// RevenueRouter.sol — refuse to restart a live sGOV reward period.
error RewardPeriodActive(uint256 periodFinish);

function distribute() external returns (uint256 treasuryAmount, uint256 govStakingAmount) {
    uint256 finish = IStakedGovToken(address(govStaking)).periodFinish();
    if (block.timestamp < finish) revert RewardPeriodActive(finish);
    ...
}
```

Alternatives, in rough order of preference:
1. Let `StakedGovToken` absorb mid-period top-ups **without** moving `periodFinish` (extend the
   rate, keep the end date) — the least disruptive to legitimate revenue routing.
2. Add a minimum interval between notifies (e.g. `rewardsDuration / 30`).
3. Enforce a minimum notify amount so dust cannot trigger a reset. This alone is weak — an
   attacker with real capital can still reset, and the donated Coin is not lost to them since it
   flows back out as rewards they partly capture.

Option 1 is strictly better than the `PreviousTrancheActive` pattern here, because reverting
`distribute()` while a period is live would also block `pullLocalReserves()` — the only path by
which reserves ever leave the lender.

## NM-010 (MEDIUM) — `MAX_DEPLOYER_STAKE_BPS` is bypassable: the Monolith allocation is unvalidated deployer input

**Discovery path.** Feynman Category 4 (assumptions): *what does `_validate` implicitly trust about
caller-supplied data?*

```solidity
// CoinDAOFactory.sol:334-342
function _validate(GovLaunchParams calldata params) internal pure {
    if (params.monolithRecipient == address(0)) revert ZeroAddress();
    if (params.deployerStakeBps > MAX_DEPLOYER_STAKE_BPS) revert DeployerStakeExceedsMaximum(...);
    if (params.deployerStakeBps != 0 && params.deployerRecipient == address(0)) revert DeployerRecipientRequired();
}
```

`monolithRecipient` is checked for non-zero and nothing else.

**The gap.** Everything in the contract signals that `MONOLITH_BPS = 200` is the protocol's own cut
and that the deployer is capped: the constant is named for Monolith, it funds a dedicated
`monolithVesting` wallet, and a separate `MAX_DEPLOYER_STAKE_BPS = 2_000` explicitly bounds what the
deployer may take. But nothing binds `monolithRecipient` to Monolith. Setting it equal to
`deployerRecipient` collapses both allocations into one beneficiary.

The factory holds `monolithFactory` as an immutable, so a protocol-controlled address *is* available
to derive or check against — it simply is not used.

**Trigger sequence (PoC `testDeployerCapturesMonolithAllocationBypassingTheCap`).**

1. Call `deploy()` with `deployerStakeBps = 2_000` (the maximum), `deployerRecipient = attacker`,
   and `monolithRecipient = attacker`.
2. Both `VestingWallet`s are created with the attacker as beneficiary.

**Measured result:**

| | Value |
| :-- | --: |
| GOV supply | 10,000,000 |
| Advertised deployer cap (2,000 bps) | 2,000,000 |
| **Actually captured** | **2,200,000 (2,200 bps)** |
| Delivered to the intended Monolith recipient | **0** |

200,000 GOV per launch — 2% of every CoinDAO's fixed supply — is diverted, and the 20% cap the
contract advertises is exceeded by 10% relative.

The attach path shares `_validate` and `_deployCoinDAO`, so it is identically affected
(PoC `testAttachPathAlsoLetsCallerRedirectTheMonolithAllocation`).

**Scope caveat, stated honestly.** How reachable the `deploy()` path is depends on the access
control of the *real* `IMonolithFactory.deploy`, which this repository cannot determine —
`novel_code.md` already flags the Monolith ABI match as an open review item. Two things hold
regardless:

- `deployForExistingCoin` needs no cooperation from the Monolith factory beyond an existing market
  whose operator opts in, and carries the same defect.
- Even if only trusted partners can deploy, the allocation is enforced by *convention* rather than
  by code. A typo in one calldata field silently sends 200,000 GOV to the wrong address, with the
  4-year vesting wallet already deployed and its beneficiary immutable.

**Fix.**
```solidity
// CoinDAOFactory.sol — bind the protocol allocation to a protocol-controlled address.
address public immutable monolithTreasury;   // set in the constructor

// then drop `monolithRecipient` from GovLaunchParams and use:
VestingWallet monolithVesting = VestingWallet(
    payable(CoreDeploymentLib.deployVestingWallet(monolithTreasury, uint64(block.timestamp), FOUR_YEARS))
);
```
If per-launch flexibility is genuinely wanted, keep the parameter but require
`params.monolithRecipient != params.deployerRecipient` and have governance or the Monolith factory
attest the address.

## Verified sound (actively challenged this pass, no finding)

- **`rewardPerToken()` cannot underflow.** Re-proved `lastUpdateTime <= periodFinish` across all
  four mutation sites, including the paths NM-011 exercises repeatedly.
- **An active reward period with zero staked supply is unreachable.** Periods only start behind a
  `totalSupply() != 0` check (`StakedGovToken.sol:101`, `:181`), and `withdrawTo` closes the period
  when supply hits zero (`:121-131`). This is what prevents NM-011 from being escalated into a
  permanent lock of `queuedRewards`.
- **Reward solvency holds under NM-011.** `_startReward`'s balance guard cannot be tripped by the
  dust attack: `newRewardRate = (leftover + reward)/D` and the balance is always `>= leftover +
  reward`, because every notified amount is transferred in first.
- **`StakingRewards` is not vulnerable to NM-011.** Its notify holder is `StakingRewardsFunder`,
  whose public entrypoint *is* gated on `block.timestamp >= periodFinish`
  (PoC `testFunderRefusesToNotifyDuringLivePeriodUnlikeTheRouter`).
- **Allocation math is exact** — the five allocations sum to `GOV_TOKEN_SUPPLY` precisely, for
  every `deployerStakeBps` in range. NM-010 is about *who receives* a share, not about the split.
- **CREATE-nonce prediction**, **quorum checkpointing**, **privilege handoff**, and
  **`deployForExistingCoin` authorisation** were re-traced and hold, as previously reported.

## Feedback-loop discoveries

- **NM-011** required both auditors. The State pass alone sees `(rewardRate, periodFinish)` rewritten
  atomically and correctly — no desync. Feynman alone stops at `onlyRewardsDistribution` and records
  the call as privileged. Only the consistency question *"why does the sibling funder guard against
  a live period when the router does not?"*, fed into the State pass's reachability map, exposes
  that the privileged role's holder has a public front door.

## Note on methodology

The first version of the NM-011 PoC **failed**, appearing to show the attack had no effect. The
cause was a harness artifact, not the contract: under `via-ir`, a local `uint256 t0 = block.timestamp`
is re-materialised from the `TIMESTAMP` opcode on each use rather than held in a slot, so
`vm.warp(t0 + i * 1 days)` compounds instead of stepping. The loop reached 465 days
(`1 + 86400 × Σ(1..30) = 40,176,001`) instead of 30, by which point everything had streamed out
regardless of the attack.

This is the same trap the 2026-07-28 run documented, hit again from a different direction. All time
arithmetic in `test/NemesisPoC2.t.sol` now derives from the compile-time constant `T0`, never from a
local copy of `block.timestamp`. **Recommend adding this to the repo's test conventions** — it has
now produced one false negative and one false positive across two audits.

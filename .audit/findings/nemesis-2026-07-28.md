## NM-006 (MEDIUM) — The lender `operator` role is irreversibly burned into `RevenueRouter`

**Discovery path.** The State pass mapped `lender.operator` as a coupled authority pair
(`lender.operator ↔ the contract able to nominate its successor`) and found **no mutation path** that
can ever move it after deployment. Feynman re-interrogation asked: *"`IMonolithLender` declares
`setPendingOperator`, and the factory calls it — so why does `RevenueRouter`, the contract that
inherits the role, never expose it?"*

**The gap.** After deployment the lender's operator is the `RevenueRouter`
(`CoinDAOFactory.sol:272-273`). `setPendingOperator` requires `msg.sender == operator`, so the router
is the **only** account that could ever nominate a successor. Its complete external surface is:

```
MAX_BPS()  acceptLenderOperator()  coin()  distribute()  govStaking()  govStakingBps()
lender()  owner()  renounceOwnership()  setGovStakingBps(uint16)  setManager(address)
transferOwnership(address)
```

There is no `setPendingOperator`, and no generic call forwarder. `acceptLenderOperator()` can only
accept a nomination the router itself cannot create. The router's lender-facing authority is
therefore permanently limited to `setManager()` and `pullLocalReserves()` (via `distribute()`).

**Compounding immutability.** `RevenueRouter`'s `lender`, `coin`, `treasury`, and `govStaking` are all
`immutable` (`RevenueRouter.sol:16-19`), and `StakedGovToken.rewardsDistribution` is `immutable`
(`StakedGovToken.sol:26`). So the router can never be replaced, and revenue can never be redirected
to a different staking contract — only diverted wholesale to the treasury via `setGovStakingBps(0)`.

**Consequences.**
1. Operator migration is permanently impossible for the lifetime of the market.
2. Any operator-only capability on the *real* Monolith lender beyond `setManager` /
   `pullLocalReserves` becomes permanently unreachable by governance.
3. If `StakedGovToken` or `RevenueRouter` is ever found defective, the only remedy is
   `setGovStakingBps(0)` (all revenue to treasury). There is no upgrade path.

**Why this branch elevates it.** On the pre-existing `deploy()` path the market is created in the same
transaction, so nothing of value pre-exists the handoff. `deployForExistingCoin` applies the identical
irreversible handoff to an **already-live market with real user funds**, in a single transaction, at
the request of its current operator (`CoinDAOFactory.sol:181`).

**PoC (passing):** `testLenderOperatorRoleIsPermanentlyLockedInRevenueRouter`
- Timelock cannot call `lender.setPendingOperator` → `Unauthorized`
- Original operator cannot reclaim → `Unauthorized`
- Exercising the router's entire owner-callable surface leaves `lender.operator()` unchanged
- `renounceOwnership()` does not release the role, it only destroys the remaining controls over it

**Severity note.** Rated MEDIUM: no attacker, no direct value loss, and `setGovStakingBps(0)` preserves
the revenue stream. **Escalate to HIGH if the real Monolith lender's `operator` role carries powers
beyond the four functions declared in `IMonolith.sol`** (e.g. collateral-factor or pause authority) —
this repository cannot determine that, and `novel_code.md` already flags the Monolith ABI match as an
open review item.

**Fix.**
```solidity
// RevenueRouter.sol — let governance hand the role to a successor router.
function setLenderPendingOperator(address newOperator) external onlyOwner {
    if (newOperator == address(0)) revert ZeroAddress();
    lender.setPendingOperator(newOperator);
}
```
Consider also making `govStaking` governance-settable, so a replacement staker can be wired without
abandoning the revenue split.

## NM-007 (MEDIUM) — Launch-window governance blackout: zero voting supply at T0

**Discovery path.** Feynman Category 5 (boundaries — *"what is true on the very first call?"*) asked who
holds votes immediately after `_deployCoinDAO` returns. The State pass then confirmed the coupled pair
`GOV distribution ↔ sGOV voting supply` is **empty on both sides** at T0.

**The gap.** Every GOV token leaves the factory into a *contract*, never an EOA
(`CoinDAOFactory.sol:301-312`): the rewards funder, the timelock, and three `VestingWallet`s whose
`start` is `block.timestamp`, so `releasable()` is exactly 0 at T0. Voting power requires
GOV → `depositFor` → sGOV → `delegate`. Therefore at T0:

- `StakedGovToken.totalSupply() == 0` — total voting power in the system is zero
- `proposalThreshold` = 10,000 GOV, `quorum` = 100,000 GOV (verified in PoC output)
- **No address can create a proposal**, so the timelock — which holds 326,732 liquid GOV — cannot act
  either, since the governor is its only `PROPOSER_ROLE` holder

**Measured blackout duration (PoC output).**

| Scenario | Time to first proposal | Notes |
| :-- | :-- | :-- |
| A whale stakes the entire Coin market at T0 and captures **100%** of tranche-0 emissions | **6 days** | absolute best case; emissions are 5,817 GOV/day |
| No Coin stakers; monolith vesting is the only liquid GOV | **74 days** | day 72 = 9,863 GOV (short), day 74 = 10,136 GOV |

Reaching *quorum* takes longer still: after 74 days of vesting-only accrual, total sGOV voting supply
is 10,136 GOV against a 100,000 GOV quorum. Realistically emissions are split across many stakers who
must then re-stake into sGOV and delegate, so the practical blackout exceeds the 6-day floor
substantially.

**Interaction with NM-006 (the reason this is MEDIUM, not INFO).** On the `deployForExistingCoin` path
the previous operator irreversibly surrenders operator authority (NM-006) to a router whose only
controller is a DAO that is **provably unable to act for at least 6 days, plausibly weeks**. During
that window nothing can change `govStakingBps`, replace the lender manager, or exercise any operator
authority. There is no admin, no guardian, and no rollback.

**PoCs (passing):**
- `testGovernanceIsInertAtLaunchBecauseNoLiquidGovExists` — `propose()` reverts with
  `GovernorInsufficientProposerVotes(proposer, 0, 10000e18)`
- `testTimeUntilFirstProposalIsPossible` — 74-day floor via vesting
- `testFastestPossibleRouteToQuorumWithAnActiveCoinStaker` — 6-day floor via emissions

**Fix options.**
1. Seed a bootstrap allocation of liquid GOV to the deployer/monolith recipient (or give the vesting
   wallets a cliff-free head start) so a proposer exists at T0.
2. Give `CoinDAOGovernor` a launch-phase guardian, or a lower initial `proposalThreshold`/`quorum`
   that governance raises once participation exists.
3. For `deployForExistingCoin` specifically: make the operator handoff reversible for a bounded
   bootstrap window (this also resolves NM-006).

## NM-009 (LOW) — Donated GOV is permanently locked in `StakedGovToken`

`StakedGovToken` inherits OZ `ERC20Wrapper`, which provides `_recover(address)` precisely so that
underlying tokens transferred in by mistake can be swept
(`lib/openzeppelin-contracts/.../ERC20Wrapper.sol`). `StakedGovToken` never exposes it and has no
other rescue path, so any GOV sent directly to the wrapper is unrecoverable and permanently
desynchronises `totalSupply()` from the underlying balance.

No solvency impact — `withdrawTo` stays 1:1 backed because the underlying balance is always ≥
`totalSupply()`. Fix: expose `_recover` behind the timelock, sweeping to the treasury.

## NM-008 (INFO) — `deployForExistingCoin` omits the zero-address check that `deploy()` performs

Feynman Category 3 (consistency): `deploy()` explicitly validates the market triple
(`CoinDAOFactory.sol:151-153`), while `deployForExistingCoin` assigns `lender.coin()` and
`lender.vault()` with no such check (`CoinDAOFactory.sol:176-177`).

Traced and **not exploitable**: a zero `coin` reverts in both the `StakedGovToken` constructor
(`StakedGovToken.sol:58`) and the `RevenueRouter` constructor (`RevenueRouter.sol:37-40`); a zero
`vault` reverts in the `StakingRewards` constructor (`StakingRewards.sol:43`) when
`StakingTokenChoice.SCoin` is selected, and is otherwise unused. Worth adding for symmetry and a
clearer revert, not a defect.

## Verified sound (actively challenged this pass, no finding)

Recorded so the team knows these were attacked, not skipped.

- **`rewardPerToken()` can never revert.** The invariant `lastUpdateTime ≤ periodFinish` was proved to
  hold across all four mutation sites (`updateReward`, `_startReward`, the `withdrawTo` final-exit
  branch, and the queue-flush early return), so `lastTimeRewardApplicable() - lastUpdateTime` cannot
  underflow. This clears a candidate permanent-DoS chain: a reverting `notifyRewardAmount` would brick
  `RevenueRouter.distribute()`, which is the *only* caller of `pullLocalReserves()` and hence the only
  way reserves can ever leave the lender.
- **Reward solvency in both ports.** The `rewardRate <= balance / duration` guard can be satisfied by
  unclaimed prior-period rewards, but every notified amount is fully transferred in beforehand
  (`RevenueRouter.sol:62-63`, `StakingRewardsFunder.sol:77-78`), so obligations never exceed balance.
  Verified by construction across exit→queue→re-deposit cycles.
- **No user-triggered rate dilution.** Unlike stock Synthetix, `_startReward` is reachable only from
  the router-gated `notifyRewardAmount` and from the `depositFor` queue flush, which is gated on
  `block.timestamp >= periodFinish`. A dust staker cannot repeatedly restart the stream while a period
  is live.
- **`deployForExistingCoin` authorisation is sound.** The `msg.sender == lender.operator()` ∧
  `lender.pendingOperator() == address(this)` pair requires two deliberate acts by the incumbent
  operator; `isDeployed` gates the lender to genuine Monolith markets; `hasCoinDAO` prevents
  re-attachment; and the accepted operator role rolls back atomically on any later failure
  (covered by `testDeployForExistingCoinRollsBackAcceptedOperatorIfRouterHandoffFails`).
- **CREATE-nonce prediction.** `_nextCreateNonce` stays in lockstep with the EVM nonce on both deploy
  paths, including the conditional `deployerVesting` branch and nested/reverting re-entry (storage and
  nonce revert together). The `PredictedRevenueRouterMismatch` assert (`CoinDAOFactory.sol:238-240`)
  makes a mis-prediction fail closed rather than silently mis-wire `rewardsDistribution`.
- **Quorum checkpointing.** The constructor checkpoint is pushed at the governor's deployment block,
  and any reachable proposal snapshot is ≥ deployment + `votingDelay`, so `quorum(snapshot)` can never
  return the empty-trace default of 0. `_optimisticUpperLookupRecent` is a faithful gas optimisation
  of `upperLookupRecent`.
- **Allocation math is exact.** Every split uses `remainder − part` chaining, so the five allocations
  sum to `GOV_TOKEN_SUPPLY` precisely and no GOV is trapped in the factory.
- **Privilege handoff is complete.** Timelock admin renounced, governor is proposer/canceller,
  router ownership → timelock, `StakingRewards` ownership renounced, all GOV transferred out.

## Feedback-loop discoveries

Both new findings came from cross-feed and neither auditor would have produced them alone:

- **NM-006** — the State pass alone sees "operator is set once, never mutated" and reads it as
  intentional immutability. Only Feynman's *"why is `setPendingOperator` in the interface but absent
  from the contract that inherits the role?"* turns that into a defect.
- **NM-007** — Feynman alone produces "there are no votes at T0", which reads as a benign bootstrap
  detail. Only the State pass's authority map shows the timelock is *also* inert (governor is its sole
  proposer), turning a latency note into a total governance blackout — and only then does its
  interaction with NM-006 become visible.

## Note on methodology

One candidate finding was chased and **disproved**: a PoC initially showed a staker accruing only
5,816 GOV over 400 days (1/365 of expected). Instrumentation traced this to a test-harness artifact —
`vm.warp(block.timestamp + 1 days)` inside a loop does not compound, because `block.timestamp` folds
to its value on entry to the test frame. Emission accrual is correct; the PoC now warps to absolute
timestamps. Reported here so the number is not mistaken for a defect later.

## Summary

- **2 new MEDIUM** (NM-006, NM-007), both structural and both amplified by the new
  `deployForExistingCoin` path; they compound each other.
- **1 new LOW** (NM-009), **1 new INFO** (NM-008).
- **5 prior findings re-confirmed**; NM-001's scope narrows on the new path.
- No CRITICAL or HIGH. No exploitable value-loss path was found: allocation math, address prediction,
  privilege handoff, reward solvency, reward-accounting underflow safety, and governance checkpointing
  were all interrogated and hold.
- The dominant risk on this branch is not an attacker — it is **irreversibility**: a live market's
  operator permanently surrenders authority to a minimal router governed by a DAO that cannot act for
  days to weeks.
